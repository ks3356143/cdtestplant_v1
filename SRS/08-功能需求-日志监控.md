# 08 功能需求-日志监控

> 路由：`/monitor/*`（日志监控菜单仅系统审计员 auditadmin 可见）；后端：`apps/system/controllers/log.py` + `apps/user/controllers.py`（日志部分）+ `utils/log_util/` + `utils/audit.py`
> 统一安全审计（7.1.6）：仅审计员可查；三类旧日志页查询仅审计员，删除受 30 天保留期保护

## 1. 数据操作日志（/monitor/operationLog）

记录**业务数据级**的操作（谁对哪张表的哪条数据做了什么）。

- 存储：`operation_log` 表（TableOperationLog）：创建时间、操作人员（外键 Users）、操作对象 operate_obj、操作详情 operate_des
- 由各业务写操作在事务内主动写入（如树节点增删改、问题单状态变更、密级标记变更等）

| 功能 | 接口 |
|---|---|
| 列表 | GET /api/system/log/operations |
| 分页列表 | GET /api/system/log/operationsPagination（仅审计员） |
| 删除（清理） | GET /api/system/log/operationsDel（仅审计员，须 ≥30 天，禁全清） |

## 2. 接口操作日志（/monitor/operations）

记录**HTTP 请求级**的访问（所有 /api 请求的方法、路径、参数、来源、结果）。

- 采集：`ApiLoggingMiddleware`（settings.py 中间件）对请求统一记录；同时输出到日志文件 `logs/root_log`
- 存储：`system_operation_log` 表（OperationLog）：请求用户、请求模块（按路径映射 API_MODEL_MAP）、请求地址、请求参数（body）、请求方式、操作说明、请求 IP、浏览器、操作系统、响应状态等；排除路径由 API_OPERATION_EXCLUDE_START 配置
- 前端页面：模块筛选、用户筛选、时间范围、关键字检索，可查看请求参数详情

| 功能 | 接口 |
|---|---|
| 列表 | GET /api/system/log/list |
| 操作日志列表 | GET /api/system/log/operations（同 1 共用） |

## 3. 登录日志（/monitor/loginLog）

- 存储：`system_login_log` 表（LoginLog）：登录用户名、IP、User-Agent、浏览器、操作系统、国家/归属地、登录类型（普通登录）、描述
- 写入时机：每次 POST /api/system/login（成功留痕；失败在 remark 记录告警，锁定告警亦写入）

| 功能 | 接口 |
|---|---|
| 列表 | GET /api/system/log/loginLogsList（仅审计员） |
| 删除 | GET /api/system/log/loginLogsDel（仅审计员，须 ≥30 天，禁全清） |

## 4. 统一安全审计（/monitor/auditLog，GB/T 28452-2012 第三级 7.1.6）

覆盖核心安全事件全程留痕、多维度检索、告警识别与日志防篡改。

- 存储：`system_audit_log` 表（AuditLog）：主体账号/角色、事件类型 event_type、事件内容 detail、结果 success、IP、User-Agent、时间；仅追加无更新入口（防篡改）
- 埋点：`utils/audit.py` 的 `audit_log(request, event_type, detail, user, success)`；事件类型常量：
  - `login_success` 登录成功（save_login_log）
  - `login_fail` 口令鉴别失败（authenticate 挂钩，含 IP）
  - `account_lock` 账号锁定告警（连续失败超限）
  - `user_change` 账号管理（用户创建/修改/删除/启停，含角色变化）
  - `clearance_change` 敏感标记变更（安全员，旧值→新值）
  - `policy_change` 安全策略变更（安全员，新旧值对比）
  - `access_denied` 越权访问告警（全局 PermissionDenied 异常处理器，方法+路径+原因）
  - `business_change` 业务数据变更（数据备份/恢复/剩余信息清理，7.1.8/7.1.9）
  - `integrity_check` / `integrity_broken` 完整性核查 / 数据篡改告警（7.1.7）
  - `security_scan` 安全性检测分析（安全员执行自检，7.1.10）
  - `log_purge` / `log_purge_denied` 审计日志清理/越权删除告警
- 告警类事件（account_lock / access_denied / log_purge_denied / integrity_broken）在审计页红色高亮
- 多维度检索：主体账号、事件类型、操作 IP、时间区间、"只看告警"；标签统计点击即筛

| 功能 | 接口 |
|---|---|
| 分页检索 | GET /api/system/log/auditLogList（仅审计员） |
| 事件类型 | GET /api/system/log/auditEventTypes（仅审计员） |

## 5. 数据完整性保护（GB/T 28452-2012 第三级 7.1.7）

重要敏感数据（项目信息、测试用例、用例执行结果、问题单）配置完整性校验标签：

- 存储：`system_data_integrity_tag`（DataIntegrityTag）：表名+行 id 唯一、digest（关键字段排序快照 SHA256）
- 刷新：受保护模型 post_save/post_delete 信号（`apps/project/tools/integrity_signals.py`）——任何写路径（含未来新增接口）事务提交后自动刷新；删除同步清标签并写审计"业务数据删除"
- 核查：审计员在统一安全审计页"立即核查"（GET /system/log/integrityCheck）批量重算摘要与标签比对；不一致即完整性破损（多为绕过应用直改数据库），逐条 `integrity_broken` 告警留痕（审计页红色高亮）
- 恢复约定：平台负责**检测与告警**；修复依赖数据库备份（dbdata.sql 导出机制）核对恢复——应用层无法凭空重建被底层篡改的内容
- 传输完整性（步骤1/2报文篡改场景）：由部署层的 TLS 反向代理提供（打包部署 `deploy/https` 8443、云上 nginx 443，均为 TLS 1.2/1.3，对外不提供明文入口）；业务处理回退由 `@transaction.atomic` 事务保证（正常写入成功、异常回滚不产生残缺数据）

| 功能 | 接口 |
|---|---|
| 完整性核查 | GET /api/system/log/integrityCheck（仅审计员） |

## 6. 日志保护（7.1.6 判定标准3）

1. 统一审计日志无更新/删除入口，代码层面防篡改
2. 三类旧日志删除接口收紧：仅审计员、仅可清理 ≥30 天（AUDIT_MIN_RETENTION_DAYS）前数据，全清/短于保留期一律 403 拒绝并写入 `log_purge_denied` 告警
3. 合法清理动作自身写入 `log_purge` 留痕（含清理条数）
4. 非审计员（admin/安全员/普通用户）访问审计接口一律 403，并生成 `access_denied` 告警

## 7. 日志监控页面通用需求

1. 日志监控菜单仅系统审计员（auditadmin）可见（前端路由 roles=["auditadmin"]，三权分立）
2. 分页 + 筛选（时间范围、用户、模块、关键字、事件类型）
3. 删除操作仅审计员且受保留期保护（后端 IsAuditor + AUDIT_MIN_RETENTION_DAYS）
4. 接口日志用于审计与排障：请求参数完整留存（注意密级项目数据同样落库，生产环境应控制库访问权限）
